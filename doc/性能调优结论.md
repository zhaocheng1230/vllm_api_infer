# 性能调优结论（910B4 实测）

> 全部数据来自**昇腾 910B4（32GB HBM）** + **Qwen3.5-4B** + `datasets/gsm8k_zh.jsonl`（1000 条）
> 模型是**混合 Mamba-Transformer**（GDN + 全注意力），不是纯 Transformer
> vllm 0.23.0 / vllm_ascend 0.23.0 / CANN 9.1.0

---

## 0. 一句话结论

| 手段 | 收益 | 状态 |
| --- | --- | --- |
| **客户端并发 64 → 256**（2卡）/ **→ 1024**（8卡） | **吞吐 +32%** | ✅ **最大收益，必做** |
| `FULL_DECODE_ONLY` 图模式 | 吞吐 +1.2%，**TTFT p95 −34%**，e2e p95 −6.5% | ✅ 已固化 |
| MTP 投机解码 | **吞吐 −15.9%** | ❌ 不用 |
| 关掉 `--language-model-only` | **吞吐 −31%** | ❌ 框架默认值，别动 |
| `max_model_len` 4096 → 2048 | 去掉多余安全余量 | ✅ 已固化 |

**服务端配置层面基本没余量了。真正的杠杆是并发。**

## 1. 客户端并发（唯一的大收益）

2 卡实测，1000 条 gsm8k_zh：

| 并发 | 墙钟 | 系统吞吐 | req/s | TTFT p50 | e2e p95 |
| --- | --- | --- | --- | --- | --- |
| 64 | 247.4s | 1557.6 | 4.04 | 0.39s | 36.7s |
| 128 | 198.2s | 1921.9 | 5.05 | 5.71s | 43.7s |
| **256** | **185.3s** | **2061.6** | 5.40 | 10.9s | 47.0s |
| 512 | 196.6s | 1946.9 | 5.09 | 33.3s | 128.9s |

- **拐点在 256 = 服务端容量（2 实例 × `max_num_seqs` 128）**
- 512 超过容量 → 纯排队 → 吞吐反降 5.6%，尾延迟爆炸
- 64 → 256：**吞吐 +32%，墙钟 −25%**

> ⚠️ **必须看 `系统吞吐`/`墙钟`，不能看 `avg_tps`。**
> `avg_tps` 是**单请求速率的平均**，并发越高请求互相排队越慢，这个数**必然下降**，跟总吞吐无关。
> 这是 v1 遗留的指标陷阱。客户端已加 `[System]` 行输出真实吞吐。

**8 卡**：`TP_SIZE=1` → 8 实例 × 128 = **容量 1024**。
起点 `CONCURRENCY=1024`，但**绝对值必须 8 卡实测**（8 实例时 PCIe/内存带宽争抢不同，2 卡的 256 只是线性外推）。
建议扫 256 / 512 / 1024 / 2048。

## 2. 服务端参数 A/B（`bench_server.py` 实测）

| 变体 | 吞吐 tok/s | TTFT p50 | TTFT p95 | e2e p95 | 判定 |
| --- | --- | --- | --- | --- | --- |
| base | 2330.39 | 6.07 | 13.57 | 41.82 | 基准 |
| `full_decode` | **2358.58 (+1.2%)** | 6.17 | **9.01 (−34%)** | 39.09 (−6.5%) | ✅ 固化 |
| `no_lm_only` | 1609.33 (**−30.9%**) | 6.21 | 24.30 | **132.55 (+217%)** | ❌ |
| `mtp`（关 lm_only + MTP） | 1163.75 (−50.1%) | 42.84 | 58.26 | 122.79 | ❌ 数据被污染 |
| `mtp_keep_lm_only` | 2038.60 (**−15.9%**) | **21.37 (+495%)** | 28.80 | 72.73 | ❌ 干净对照 |

### 2.1 `FULL_DECODE_ONLY` ✅

```json
"extra_args": ["--compilation-config", "{\"cudagraph_mode\":\"FULL_DECODE_ONLY\"}"]
```

零代价换尾延迟改善，无副作用。

> ⚠️ **不要手动指定 `cudagraph_capture_sizes`。**
> 限死成 `[2,16]` 而实际 batch 是 128 → **pad 不下去**（只能往上 pad）→ 全图路径完全用不上
> → 吞吐反而 **−5.3%**。用默认值（覆盖到 `--max-num-seqs`）才是对的。

### 2.2 MTP 投机解码 ❌

模型**支持** MTP（`config.json` 里 `mtp_num_hidden_layers: 1`，safetensors 里有 `mtp.layers.0.*` + `mtp.fc.weight`），
但实测 **−15.9%**，TTFT p50 **+495%**（3.59s → 21.37s）。

原因：
- `num_speculative_tokens: 1` → 理论上限才 2x
- 4B 小模型的 MTP 头只有 1 层，猜测质量差 → **接受率低**
- 接受率低 → 白跑草稿前向 + 验证 batch 翻倍 → 净亏损
- 第三方那个 1.23x 是 **397B MoE** 的数字，稠密小模型不适用

### 2.3 `--language-model-only` ❌ 别关

框架对 Qwen3.5 自动加这个参数（+ `qwen3_coder` parser）。实测关掉 → **吞吐 −31%，e2e p95 +217%**。
它不只是"跳过多模态"，还切换到了更快的执行路径。**保持框架默认。**

## 3. 踩过的坑（都是框架/流程问题，不是性能问题）

| 坑 | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| `avg_tps` 当吞吐看 | 并发越高数值越低，误判为"并发无用" | 单请求速率的平均 | 看 `[System] 系统吞吐` / 墙钟 |
| argparse 前缀匹配 | `--input` 被静默绑到 `--input_dir` → "找不到文件"但退出码 0 | `--input` 是 `--input_dir` 的前缀 | 客户端加 `--input`；框架开跑前 grep 源码做版本检查 |
| 目录扫描 | 拿文件路径去 `glob("*.jsonl")` → 空 | 旧测试逻辑 | 改成直接读唯一文件路径 |
| 假成功 | 找不到输入 / 全部条目失败 → 退出码 0 → 上层报"全部完成" | `return` 而非 `sys.exit(1)` | 失败一律退出码 1，管道遇错立即中止 |
| 空参数 | `vllm: error: unrecognized arguments:` → 服务起不来 | 标量 `EXTRA_CHUNKED_ARGS=""` 被数组惯用法展开成空参数 | 改用条件追加 `SERVE_CMD+=(...)` |
| `capture_sizes` 限死 | 图模式反而 −5.3% | batch 128 pad 不下去 | 用默认值 |
| Triton kernels 导入失败 | `cannot import name 'constexpr_function' from 'triton.runtime.jit'` | 环境里装了 3 个 triton 包（`triton` / `triton_ascend` / `tokenspeed-triton`）互相覆盖 `triton/` 目录 | 未处理，不影响启动（但可能影响融合算子） |

## 6. 高并发下的连接池雪崩（2026-11-02 实测定位）

**现象**：910B4 + 4 实例（TP=2），并发 256 → 512 后：

| 指标 | 并发 256 | 并发 512 |
|---|---|---|
| 墙钟 | 1627.4s | 1434.4s（−11.8%）|
| 系统吞吐 | 2370.3 tok/s | 2715.8 tok/s（+14.6%）|
| TTFT p50 | 11.8s | **87.5s** |
| 端到端 p95 | 481.2s | 940.6s |
| **重试次数** | **5 次** | **200+ 次** |

**根因**：`init_client_async` 里 `pool_size = max(512, concurrency + 32)`
- 并发 256 → pool=512，余量 **256** → 重试只发生 5 次
- 并发 512 → pool=544，余量 **32** → 重试请求把余量挤爆 → 新请求在 httpx 池里
  等到 `pool=120s` 超时 → `httpx.PoolTimeout` → openai 映射成 `APITimeoutError`
  → 更多重试 → **雪崩**
- nginx `proxy_read_timeout 86400s` 不掐断 → 服务端旧请求还在跑，slot 不释放，
  重试等于把已经算过一遍的请求重做

**修复**：
```python
pool_size = max(512, concurrency * 2 + 64)   # 余量按并发倍数给
pool=max(120.0, read_timeout)                # 等池位不能比等响应还短
```

**附带结论**：
- **服务端峰值能力 4 × 2000 = 8000 tok/s**，gpqa 那轮只跑到 2370 是**尾部效应**
  （792 条 ÷ 并发 256 = 只有 3.1 波），不是能力上限
- **KV 峰值只有 22~32%** → 显存不是瓶颈，`max_num_seqs`（TP=2 档位 128）还有空间
- **`--max-num-partial-prefills 1`**（TP>1 固化参数）**从未做过 A/B**，
  高并发 + 长 prompt 场景下可能是隐藏瓶颈 —— 待测

## 7. 并发 512 的 ConnectTimeout 雪崩（2026-11-03 定位并修复）

**最终根因**：`nginx listen` 没写 `backlog`（默认 511）。

```
并发 512 → 512 条流式连接常驻（httpx 无法复用）
    ↓
重试/新请求只能新建 TCP 连接 → 瞬时上千条连接要建
    ↓
SYN 队列（511）满 → 内核丢 SYN → TCP 握手重传 1s/2s/4s…
    ↓
超过 httpx connect=30s → ConnectTimeout → 重试 → 雪崩
```

**这个根因解释了此前所有矛盾**：
- nginx 只收到 793 条 → 那 200+ 次重试**压根没连上 nginx**
- 客户端端到端 p95(878s) > nginx request_time max(756s) → 客户端多花了 ConnectTimeout 的 30s + 重试
- **TTFT p50 87s**（查了很久的那个）→ **不是服务端排队，是 TCP 建连等待被算进了 TTFT**

**修复**：
```nginx
listen {{LISTEN_PORT}} backlog=8192;     # 默认 511 太小
keepalive 1024;                          # upstream keepalive 128 → 1024
```
```python
connect=120.0                            # 30s → 120s
```

**⭐ 排查方法论（这次绕了 4 轮弯路）**：
1. **openai 把所有 httpx 超时都包成 `APITimeoutError`**，必须打 `exc.__cause__` 才能区分
   `ReadTimeout`(服务端慢) / `ConnectTimeout`(连不上) / `PoolTimeout`(池挤爆) / `RemoteProtocolError`(被断开)
2. **access_log 加 `buffer=32k flush=5s` 会丢日志** —— 任务结束 stop nginx 时缓冲区里的记录全丢，
   正好把最慢的那批（要排查的）弄没了。**去掉 buffer**（几千条的量级，直接落盘无压力）
3. **nginx request_time 与客户端端到端矛盾**（客户端 > nginx）→ 说明那批请求**没进 nginx**，
   指向「连接就没建起来」而不是「服务端慢」

## 8. 并发 512 的 TTFT 90 秒 = prefill 排队（2026-11-03 定位）

**修复 ConnectTimeout 后的实测**（重试 200+ → **0** ✅）：

| | 并发 256 | 并发 512（旧）| 并发 512（修完 ConnectTimeout）|
|---|---|---|---|
| 墙钟 | 1627.4s | 1434.4s | **1413.2s** |
| 系统吞吐 | 2370.3 | 2715.8 | **2729.7** |
| 重试 | 5 | 200+ | **0** ✅ |
| TTFT p50 | 11.8s | 87.5s | **90.6s** ⬆️ |
| 端到端 p50 | 237.4s | 403.3s | 392.8s |

**TTFT 90s 是独立问题，不是 ConnectTimeout 造成的。**

**⭐ 客户端 ttft 只有两种值：`0.001s` 和 `90~113s`** ——
因为 `start_time` 是在 `await create()` **之后**取的：
- `ttft=0.001s` → create() 阻塞了 90 秒（服务端排队），拿到 headers 立刻出 token
- `ttft=90s` → create() 立刻返回，第一个 content chunk 等了 90 秒
**两者相加 = 每个请求从发出到拿到首 token 都等了 ~90 秒。**

**根因：prefill 排队，`max_num_batched_tokens=16384` 不够**
```
512 并发 → 每实例 128 个请求同时到达 → 每个都要 prefill（prompt ~2000 token）
    → vLLM 每步最多处理 max_num_batched_tokens 个 token
    → 128 个请求的 prefill 分成十几步排队 → 首批请求堵 ~90 秒
```
**验算**：并发 256（每实例 64 个）→ prefill 步数减半 → TTFT p50 = 11.8s ✓

**旁证**：gpqa 吞吐峰值 2000 tok/s，supergpqa 只有 1080 —— prompt 越长 prefill 越重。

**修复**：`max_num_batched_tokens` 16384 → **32768**（KV 峰值只有 45%，还有空间换更大的 batch buffer）
`--max-num-partial-prefills 1` 暂不动 —— prompt(2000) < 16384，不会触发 chunked prefill，该参数大概率没生效。

**⭐ 下一步判据**：
```bash
grep -o "Avg prompt throughput: [0-9.]*" vllm_*.log | tail -4
grep -o "Avg generation throughput: [0-9.]*" vllm_*.log | tail -4
```
**prompt 吞吐接近 generation 吞吐 → prefill 是瓶颈 → 继续提 batched-tokens**

## 9. 最终推荐参数（2026-11-03 定稿）

### 9.1 服务端档位

```bash
set_server_params() {
    case "$1" in
        1) MAX_NUM_SEQS=128; MAX_NUM_BATCHED_TOKENS=32768; TP_EXTRA_ARGS=() ;;
        2) MAX_NUM_SEQS=256; MAX_NUM_BATCHED_TOKENS=16384; TP_EXTRA_ARGS=(--max-num-partial-prefills 1) ;;
        4) MAX_NUM_SEQS=128; MAX_NUM_BATCHED_TOKENS=32768; TP_EXTRA_ARGS=(--max-num-partial-prefills 1) ;;
        8) MAX_NUM_SEQS=128; MAX_NUM_BATCHED_TOKENS=65536; TP_EXTRA_ARGS=(--max-num-partial-prefills 1) ;;
        *) MAX_NUM_SEQS=128; MAX_NUM_BATCHED_TOKENS=16384; TP_EXTRA_ARGS=() ;;
    esac
}
```

### 9.2 客户端并发对应表

| 卡数 | TP | 实例数 | max_num_seqs | batched_tokens | **客户端并发** | 依据 |
|---|---|---|---|---|---|---|
| 2 | 1 | 2 | 128 | 32768 | **256** | 实测拐点（2061 tok/s）|
| 4 | 1 | 4 | 128 | 32768 | **512** | 外推 |
| **8** | **2** | **4** | **256** | **16384** | **256** | **实测最优** |

**⭐ 实测确认（并发 256，max_num_seqs=256，util 0.85）**：
```
TTFT p50 = 0.001s   端到端 p50 = 217.9s   p95 = 641.3s   avg_tps = 18.0   重试 0
```
**并发 512 同一配置下：TTFT p50 = 90.6s、端到端 p50 = 392.8s、p95 = 992.6s、avg_tps = 10.2**
→ **延迟全面减半、单请求速率高 76%，整批只慢 8%（尾部效应）**

**⭐ `max_num_seqs` 的真正作用被这轮实测揭示了 —— 它决定「一次能拉多少请求进 prefill」**：
```
max_num_seqs=128 + 每实例 64 请求 → 占 50% → TTFT p50 = 11.8s
max_num_seqs=256 + 每实例 64 请求 → 占 25% → TTFT p50 = 0.001s ✓
```
| 8 | 4 | 2 | 128 | 32768 | **128** | 推算 |
| 8 | 8 | 1 | 128 | 65536 | **64** | 推算 |

**规则：并发 = 实例数 × 每实例并发（TP=1 → 128，TP≥2 → 64）**

### 9.3 ⭐ 为什么 8 卡选 256 而不是 512

**并发 512 的"吞吐高 15%"是尾部效应造成的假象**：
```
并发 512 -> 4 实例 × 128 个/实例 -> 每实例瞬时峰值 2000 tok/s
并发 256 -> 4 实例 × 64 个/实例  -> 每实例瞬时峰值 2000 tok/s
```
**稳态吞吐完全一样（8000 tok/s）** —— 批大小翻倍，每请求速率减半，总吞吐不变。

差异全在波数：792 ÷ 512 = 1.55 波（尾部 280 条空转）vs 792 ÷ 256 = 3.09 波（尾部 24 条）。

**折算到 20994 条（41 波，尾部效应可忽略）**：

| 并发 | 稳态吞吐 | 20994 条耗时 | 端到端 p50 | 端到端 p95 |
|---|---|---|---|---|
| **256** | 8000 tok/s | **3.6 小时** | **237s** | **481s** |
| 512 | 8000 tok/s | 3.6 小时 | 393s | 993s |

**吞吐一样、延迟差一倍 → 生产场景选 256。**

**⭐ 并发 512 唯一的适用场景：数据集很小（< 2000 条），想快速跑完。**

| 项 | 值 | 依据 |

## 10. prefix caching：不开（2026-11-03 决策）

**实测 vLLM 0.23.0 + vllm-ascend 默认 `enable_prefix_caching=False`**，日志里命中率恒为 0.0%。

**但我们的场景不开更好** —— 单轮批量推理，没有多轮对话那种大段公共上下文：
```
共享前缀 = chat template + system_prompt ≈ 50~75 token
每条请求 prefill ≈ 2000 token
收益 ≈ 75/2000 × (prefill 占总工作量 29%) ≈ 1%
```
**1% 的收益 vs prefix caching 的记账开销 + 混合 Mamba 模型的支持风险 → 不值得。**

**⭐ 什么时候该开**：多轮对话场景（公共上下文几千 token 以上），或同一条 prompt 反复问。

**⭐ 顺带确认的两个启动参数（vLLM 0.23.0）**：
- `enable_prefix_caching=False`（默认关）
- `enable_chunked_prefill=True`（默认开）
  → **`--max-num-partial-prefills 1` 是生效的**，它限制「同时只允许 1 个请求做分块 prefill」。
  在高并发 + 批量 prefill 场景下会把 prefill 串行化。
  **⚠️ 下一步可试：`--max-num-partial-prefills 4`**（并发 512 时 TTFT 90 秒的候选修复）
